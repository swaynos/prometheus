# Product-to-cart workflow (manual checkout)

This is an operator procedure using existing `prometheus-browser` tools, not an automated retailer integration. A controlled local fixture exercises the steps through the real MCP and Chromium; **no real storefront cart or checkout has been qualified**. Select backend, mode, authentication and recording under the browser reference and applicable policy before starting. Use a dedicated automation profile. No cart mutation on a real store is authorized without explicit approval for the exact product, variant, quantity and intended cart change.

## Boundaries and handoff

Before launching, obtain the user's explicit choice of managed `executionMode: "headed"`, a dedicated automation profile, and a graphical session the user can actually access. Do not change mode in reaction to a denial. This mode retains the task browser, page, proxy owner and named generation rather than moving state to a second context. The managed headless task browser is not human-interactive and cannot be converted; stop and report the limitation, without closing and reopening it. Linux virtual-display is not automatically a human-accessible desktop and is not accepted for this takeover. The headed login helper is a **separate context** for authentication capture, not the live cart. Do not export storage, cookies or credentials, switch routes, or rotate a proxy. Configured session and generation pin one configured endpoint, not a guaranteed exit IP.

After exact cart verification, obtain the user's actual consent, then call `browser_takeover` with `user_requested: true`; the boolean does not authenticate a person. The queued call runs after earlier operations finish; if a mutation was interrupted, its outcome is unknown and must be reconciled first. On success, tell the user the existing window is theirs and end the turn. During takeover all agent tools except metadata-only status, close, and handback are rejected; do not invoke close while the user is working. No recording, polling or automation occurs. Tell the user to finish manually and to avoid leaving payment or other secret information on the page for subsequent inspection. Only after their explicit handback confirmation call `browser_handback` with `user_confirmed: true`; this declaration is not proof of human identity. A closed original page, lost context, or changed proxy generation/owner fails closed. After handback, `browser_snapshot` of the original page is required before other actions; inspect only non-secret page content, and do not resume if it may expose sensitive information. Handoff is not proof of checkout or order completion. A real human-accessible desktop and real retailer checkout remain unqualified.

If a user has independently selected and provided a human-accessible external CDP task browser, pause all agent actions and leave that actual page open for them; first establish that the user can access it and that the selected workflow permits this. External CDP does not support the managed proxy configuration; it is not a fallback or conversion of an existing managed task. Do not start or reconfigure one to work around denial. Never automate checkout, payment, or order placement. When control returns, inspect the page before any further action; do not poll for the human.

## Procedure

1. Obtain the exact product URL, requested variant, quantity and approved cart mutation. Record the selected backend/mode/session. Navigate with a bounded timeout. Stop on 401/403, proxy failure, managed challenge (including HTTP 200 challenge pages), or unverified navigation. No automatic retry, direct fallback, rotation or diagnostic workaround. The opt-in 2captcha capability is only for separately authorized standalone Turnstile cases; it is not a generic managed-challenge solver.
2. Inspect `browser_status`, `browser_snapshot`, `browser_interactive_elements` and, where useful, visible DOM records with `browser_extract`. Confirm final origin and product identity match the requested URL and the visible name/product details. A synthetic example is `https://shop.example/product/fixture-item-001`; it is not a real storefront. Current content, stock, controls and redirects must be freshly inspected. Product JSON-LD may provide corroborating identity/offer data, but is optional and can be stale or inconsistent. Do not rely on hidden JSON-LD alone, infer stock from a missing offer, or assume its structure. If identity, availability, selected variant, or price/offer are ambiguous or conflict with visible evidence, stop and ask. Use `browser_evaluate` only where permitted by the runtime, narrowly for non-secret product metadata; it is disabled with hydrated saved state. Never extract authentication data.
3. Require positive, unambiguous visible in-stock evidence for the requested variant and a visible enabled purchase control. Inspect controls afresh; choose the requested variant with `browser_select_option` or a visible control, set quantity with `browser_fill` or an observed quantity control, then re-inspect and verify the actual selected variant and quantity, availability and enabled state. Do not substitute options or quantities. If not determinable, stop. Selectors in the fixture are illustrative, not storefront selectors.
4. Inspect the current cart first where supported. Compare all items, variants and quantities to the desired final cart. If already exact, do not add again; if additional items or an unclear baseline prevent an exact outcome, stop and ask rather than remove or change them without approval. Immediately before a non-idempotent add, record intent (product, variant, quantity, baseline and one authorized click). Click once using `browser_click` with a bounded, fresh page-change expectation when available. A response or confirmation alone is not proof of cart contents.
5. After any timeout, cancellation, lost connection or unknown result, mark outcome **unknown**. Do not replay. A single browser click does not guarantee one backend request: Chromium or transport may retry after connection loss, even for POST. Inspect the original page first, then the cart using visible UI if safe; reject duplicate or otherwise non-exact cart contents, and if still unresolved stop and request human review. A retry requires a new explicit decision and authorization based on the inspected state, never an automatic repeat. Do not invent an idempotency guarantee or remove duplicates without authorization.
6. Navigate to the cart through observed UI, inspect every line and quantity, and confirm exactly the desired product, variant, quantity and no unexpected lines. If unavailable or conflicting, report unverified; do not claim success. Then pause for the same-live-session handoff described above. No checkout action is authorized by cart approval.

Run controlled fixtures with `node --test tests/integration/browser_shopping_workflow.test.mjs tests/integration/browser_takeover.test.mjs`. The shopping test uses synthetic server-backed cart data; takeover uses a test-only launch substitution to exercise the gate with a real headless browser and local proxy lease, not a human-visible desktop. Neither qualifies live retailer layout, real stock, a real proxy provider, or a human handoff.
